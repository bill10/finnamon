D-numbers below (D4, D10, ...) refer to decisions Bill made during the office-hours session.

## Problem Statement

Finnamon is a working Plaid-backed personal finance web app (Next.js + FastAPI + Celery + Postgres, deployed on Vercel + Cloud Run). Bill built it, deployed it, and doesn't open it. The background sync has a history of silent failures (Celery workers not running, double-negated amounts, IRA/401k holdings bugs). The app shows data; it never tells him anything.

Rewrite it, keeping the name, as a household finance agent: one assistant that watches the household's accounts and comes to whoever needs to know when something needs a human. A one-person household is the degenerate case; the design is the same.

## Principle: build the infrastructure, not the agent

Arrived at with Bill during the user-workflow walkthrough: **Finnamon builds the infrastructure an agent needs; it does not build the agent.** Claude Code is the agent: reasoning, tool calling, permissions, sessions, compaction, skills. Finnamon supplies what the harness can't have on its own.

| Finnamon builds | Claude Code provides |
|---|---|
| Data layer: Plaid sync, SQLite schema, sign conventions, dedup | Judgment: what's worth mentioning, what "it is normal" means |
| The daemon: always-on, Telegram in/out, sync clock | Conversation: sessions, memory, compaction |
| Deterministic detectors: SQL that says what happened | Skills: `/triage`, the finnamon skill, editable in English |
| The CLI: every read and write as a command Claude can run | Tool calling and permissions (`.claude/settings.json`) |
| Notifications and heartbeat: the zero-token path that must work when Claude is down | Everything that needs a model |

Test for any new feature: is it infrastructure Claude Code lacks (a detector, a CLI verb, a data source), or is it re-implementing something the harness already does (parsers, prompt templating, conversation state, action validators)? Build the first kind; delete the second. This walkthrough deleted three of the second kind: keyword reply parsers, a JSON action vocabulary, and a bespoke triage prompt.

Corollary: the daemon exists only because Claude Code isn't always on and can't notify anyone. If the harness ever grows a scheduler and an outbound channel, the daemon shrinks to sync alone.

## What Makes This Cool

A message from your own money: "Netflix charged you twice on 9/14, $15.49 each. Want me to draft the dispute?" Or on the 18th: "Groceries: $480 of $600, on pace for $780." Or, the one Bill named as the real differentiator: "$412 to 'SQ *PMT 8827' on the Amex yesterday. You've never paid this merchant, it's 6x your usual Square charge, and I can't tell what it is. Recognize it?" The agent finds things you don't know, the way a human assistant reading your statements would. Nothing in the space does this.

The 10x arc, all of which this design leaves room for:
- Two-way in the chat: reply "normal 3" and item 3 of the roundup becomes a suppression; "set groceries 650" changes the budget; "watch for X" and Claude drafts a detector for review.
- CFO picture: net worth, investments, forecasting, monthly memo.
- Household from day one: a partner's Items, one shared chat, one shared assistant.
- Publishable: anyone with an always-on box, a Plaid trial key, a Telegram account, and Claude Code can run it.

## Constraints

- Household tool, builder mode. No customers, no pricing. One agent per household with one identity, one memory, one data store; people who want separate assistants install separately (Bill's call).
- Runs on any always-on box Bill owns: his Mac today, an Ubuntu machine or a Pi later. No cloud service of ours.
- Plaid Trial plan: 10 Items max, free, real data. Transactions + Balance first. Exact per-product call limits and whether Recurring Transactions is included are verified in The Assignment before the cadence is fixed.
- Detection never touches an LLM. Rules fire on SQL alone. The only LLM work in the unattended path is anomaly triage, a Claude Code skill that runs only when candidates exist; zero tokens otherwise.
- Reproducibility, stated precisely: transaction-derived detectors replay from the DB with the stored `as_of` (all joins to `merchant_alias` and `suppressions` are time-scoped to `as_of`). Item- and stream-derived detectors (`sync_health`, `new_recurring`, `recurring_changed`) replay from `payload_json`, because `items` and `recurring` are upserted in place. Triage verdicts are stored, never recomputed.
- The watchdog watches itself: a dead sync, a dead scheduler, or a dead triage is an alert, not a silence.
- Merchant text and reply text are untrusted input. They never get interpolated into shell or SQL.

## Premises (agreed)

1. No standing dashboard. Telegram out (text, and chart PNGs on demand), Claude Code in. Bill: "I don't need a UI there every minute, but I might want the agent to show me something in charts not words."
2. Plaid Trial plan is the data source; institutions fit in 10 Items. Investments/Liabilities added later (billing only matters if we ever upgrade past trial).
3. Two tiers of detection. **Rules** (duplicate, new recurring, low balance, budget pace, sync health) are deterministic SQL over Plaid-normalized fields and fire on their own. **Anomalies** ("this looks strange," "no clear source") are SQL candidates triaged by an LLM that decides whether a competent assistant would mention it, with what confidence, and why; it can promote or suppress a candidate, never invent one, and every verdict is logged. Merchant aliases and suppressions are written only by Bill (CLI or reply parsers), never by the LLM. (Amended after Gemini's challenge and after Bill named "things I don't know" as the differentiator, D13.)
4. Delivery is a Telegram bot in one household chat (a DM while there is one owner, a group once there are two). Replaces iMessage (D3) after Bill asked about Android and Ubuntu: iMessage locks the sender to a Mac and the receiver to Apple devices; Telegram's Bot API is plain HTTPS from anywhere, sends text and photos, and delivers replies by long-poll with no OS permissions. Known cost: bot messages are not end-to-end encrypted, so merchant names and amounts transit Telegram's servers. No account numbers or credentials are ever sent. Bill accepted this.
5. Scheduling is launchd on macOS, a systemd timer on Linux, plain cron only on a host that never sleeps. Reason: cron skips a job the machine slept through; launchd `StartCalendarInterval` and systemd `Persistent=true` run it on wake. `finnamon init` detects the OS and installs the right one.
6. The web app goes away entirely: FastAPI, Next.js, Celery, Postgres, Vercel, Cloud Run, both submodules. Old `backend/app/services/plaid.py` is kept as `reference/old_plaid.py` for the sign-convention tests until `sync.py` passes them, then deleted.
7. Doing nothing = a deployed app nobody opens and a sync nobody trusts. Real pain.
8. Budgeting is category limits with pace alerts, not envelopes. A budget is a detector, not a screen. (D12.)
9. Anomaly delivery is split by confidence: high-confidence (fraud-shaped: unknown source, large, first-ever) goes out in the next run; the rest batch into one weekly "things I noticed" message. (D13.)

## Cross-Model Perspective (Gemini CLI 0.55.1, cold read)

- Coolest unconsidered version: reply "watch for X" and the LLM writes a new SQL detector on the fly. Adopted as the north star for the reply loop, with a guard: generated detectors are read-only SELECTs reviewed in Claude Code before they go live.
- Most revealing thing Bill said: "the first text should be a genuine catch." High-signal utility, not vanity metrics.
- Challenged the SQL-only premise: merchant strings like "Netflix.com" vs "NFLX* SUB" will defeat pure SQL. Accepted in part; premise 3 amended. Plaid's normalized fields and recurring endpoint do most of the work; the alias table and the anomaly tier catch the rest.
- Suggested Open Finance as a 50% base. Rejected; see below.
- Recommendation: "Delete the old repo today and write a single Python script that texts you your balance." Spirit accepted (delete the old app now); letter rejected (the first message is a catch, not a balance).

## Why not Open Finance (or Ledgr)

Checked by cloning `DeseretSaint/open-finance` v0.3.15 (46.7k lines TS, MIT) during the session:
- Sync scheduler runs inside the Next.js server (`src/instrumentation.ts`); unattended sync means a permanent web server.
- Notifications are a daily/weekly email digest of budget names and status; the code says it "deliberately does NOT include account numbers or transaction-level detail." Opposite of a watchdog.
- No alert rules, no duplicate or recurring detection, no pace alerts, no anomaly triage. `transactions` has `merchant_name` and `personal_finance_category` but no `merchant_entity_id`, and there is no recurring-streams table.
- The MCP layer (30 tools, scoped tokens, guardrails, agent manual) is the best part and is prior art for milestone 5.

What distinguishes this design: push-first (no place to go), the agent notices what you don't know, detectors as reviewable SQL artifacts, two-way in chat, and no UI to maintain. The Plaid sync we'd have borrowed is one file. If the goal were "a finance app Claude can query," Open Finance is the right answer and this rewrite shouldn't happen; Bill confirmed the push loop is the product (D11).

## Approaches Considered

- A: Three scripts + a scheduler, B's schema up front. Minimal loop, zero-token cron, first catch this weekend. Ruled out by Bill in favor of B: he wants every 10x direction to have a home now (D10).
- C: Claude Code is the cron (the scheduler runs `claude -p "/watchdog"` headless). Ruled out for unattended alerts: tokens on every run, and a permission prompt at 6am means no message and no error. Its trick (a skill that runs the whole loop by hand) is kept for the reply side, with the invocation pinned down in milestone 4.
- iMessage delivery (D3): superseded by Telegram (premise 4). It would have needed osascript, two macOS TCC grants, and a `chat.db` parser for replies, and it could never reach an Android phone.
- Prose composition of rule alerts via `claude -p`: considered and dropped. Five rule templates are five sentences, anomalies already carry a triage reason, and it would put an LLM in the rules path.

### Step 3: Claude proposes budgets from history (reviewed)

Bill's point: Steps 1 and 2 involve credentials so a human does them; budgeting is tedious and an AI should do the work. Claude Code is the interactive surface, and nobody has to learn Plaid's category names.

```
$ cd ~/finnamon && claude
> set up my budgets
```

The skill runs `finnamon budget suggest --json` (SQL over the backfill: spend by `pfc_detailed` per month for 6 months, median and spread, recurring vs variable, per-merchant share) and Claude reasons over the numbers:

> I looked at 6 months of your transactions. Starting point, rounded up a little from your typical month:
>
> | # | Budget | Proposed | Last 6 months | Notes |
> |---|---|---|---|---|
> | 1 | Groceries | $650 | $540–$720, median $610 | Costco is 40% of this. Plaid files it as "superstore"; I'm counting it as groceries for you. |
> | 2 | Dining | $350 | $280–$410 | |
> | 3 | Gas | $150 | $110–$160 | |
> | 4 | Subscriptions | $75 | $68 flat | Stable; I'd skip a budget and just alert on new ones. |
> | 5 | Shopping (Amazon, Target) | $300 | $90–$560 | High variance. Budget or just watch? |
>
> Not proposing: rent ($2,400, fixed), insurance ($142, fixed), transfers to savings. Fixed costs get watched, not budgeted.
> Adjust anything, or say "looks good."

> **groceries 700, drop subscriptions, and add a pets budget around 80**

> Done. Groceries $700. Subscriptions removed (new recurring charges still alert). Pets: Chewy and Banfield, $62–$95/month, set to $80.
> Your Chase Checking dipped to $640 on Aug 28 before payday. Want a low-balance alert at $1,000?

> **yes**

> Set. 5 budgets, 1 threshold. You'll hear from me when a budget is on pace to go over, not before.

Underneath: Claude proposes and groups; every write goes through a CLI primitive (`finnamon budget set groceries 700`, `finnamon category costco GROCERIES`, `finnamon threshold "Chase Checking" 1000`). All of them write SQLite (`budgets`, `category_override`, `settings`); none touches `secrets.toml`. The tables written are the ones the detectors read. Tokens spent once, at setup. Nothing bypasses the primitives, so the same commands work with no model at all.

Consequences for the design:
- `category_override` is a day-one table (see schema). Claude needs it to say "counting Costco as groceries."
- A budget may target a `pfc_primary` (all of TRANSPORTATION) or a `pfc_detailed`; `budgets.category` holds either and the detector matches accordingly.
- Category name resolution is deterministic: token match on Plaid's names, a shipped synonym table, then a numbered list. Claude does the resolving in this step; the CLI never guesses.
- Budgets are set in Claude Code at setup and adjusted in Telegram once the reply loop exists (milestone 4). From milestone 2 the monthly roundup may propose adjustments ("Dining ran $420 against $350 three months running. Raise it to $400?").

In the group: "Jane is linked. Chase Checking and Savings are joint. Everything I notice goes here from now on."

Rules from then on:
- **Everyone is notified about everything, in one chat** (Bill's decision on the last question of the walkthrough). One identity, one memory, one thread; the group on your phones is the agent's record. Per-owner routing was dropped because a reply in a private DM would put knowledge into the shared session that the other person never saw. Each person can mute the group in Telegram; alerts are a few a week by design.
- **The whole household shares visibility** (Bill: "No need for access control. The whole household share visibility. If two people in the household want separate assistants, they should just install it separately"). Jane can ask what Bill spent on the Sapphire and get an answer.
- `accounts.owner` is a fact the agent knows ("that's Bill's card"), used in message text and queries, not for routing.
- **Budgets are household-level. There is one set of budgets, no owner column** (Bill: "No need for personal budget. Just one budget for now"). Every account of every owner counts toward them. Budget pace alerts go to every owner.
- Match heuristic at link, in order: Plaid `persistent_account_id` when the institution supplies it; else same institution + `mask` + `subtype` + at least 90% of the last 90 days' transactions matching on (date, amount, name). Below that: distinct, no prompt. `finnamon account merge|unmerge` fixes mistakes.
- Both Items sync every account fully; nothing is skipped. The duplicate account row carries `mirror_of = <primary account_id>`, and `_prelude.sql` excludes transactions whose account is a mirror. If the primary Item breaks and the mirror's Item is healthy, failover is flipping which row is the mirror; no cursor reset, no re-backfill, no gap (eng review, Gemini tension 3).
- Knowledge is shared: suppressions, category overrides, budgets, and the conversation itself belong to the household. When Jane says "it is normal," the agent does not ask Bill about that merchant later.

### Step 7: Talking to it (reviewed; architecture settled with Bill)

Bill: "we shouldn't rebuild a harness, claude code is already a really good one and we should use it as much as we can." So replies are not parsed by keyword; every message goes to Claude Code, which is the harness.

**Process model.** One long-running `finnamon daemon` (kept alive by launchd/systemd) long-polls Telegram and runs sync on its own 6-hour clock. A separate hourly heartbeat timer watches the daemon. Claude Code is on demand: `cd ~/finnamon && claude` picks up the skill from the repo.

**Experiment (v0.4.0.0): Claude Code's own Telegram channel.** `finnamon channel on` sets `state.inbound=channel`: the daemon's Telegram thread acknowledges its last `getUpdates` batch (else the plugin's first poll would replay it), stops polling (Telegram allows one `getUpdates` consumer per bot) and only stamps `daemon_alive_at`, while sync, detect, triage and alert sending continue unchanged. The conversation then runs in a `claude --permission-mode dontAsk --channels plugin:telegram@claude-plugins-official --disallowedTools WebSearch WebFetch` session the household keeps open; `dontAsk` because the plugin would otherwise relay permission prompts to paired phones as Allow/Deny buttons. The bot token is copied by hand to `~/.claude/channels/telegram/.env` (on the Read deny list). Enrolment is `finnamon owner add <name> --user-id <id>` (the plugin's pairing gates who may talk; Finnamon only needs the id to attribute speech), and the code dance is refused at the source in channel mode. `finnamon channel off` returns to the loop below; `finnamon status` shows `inbound`. Because that session is then the bot's only reader, the daemon watches it from outside (v0.7.2.0): once a minute it asks `getWebhookInfo` how many updates Telegram is still holding, which reads the backlog without collecting it and so cannot take the one slot from a live plugin. A backlog that sits for `DEAF_AFTER_S` (300s, well past the slowest Claude turn) stamps `state.channel_deaf_since` and raises a `channel_deaf` alert, sent immediately rather than at the next cycle: sending works while receiving is broken, which is the only reason the outage is reportable at all. `DEAF_REPEAT_H` (6h) is the floor between tellings, so a reader that crash-loops cannot flood the chat. The stamp clears when the backlog drains and on `channel off`; `status` and the dashboard pill both show it, behind `daemon_alive` because only the daemon clears it. A 409 from `getUpdates` backs the daemon off 10s, then 60s; the third in a row posts one notice to the chat and sets `state.inbound_conflict_at`, which `status` shows until a clean poll or `channel on` clears it. The plugin acks a batch as it takes it, so a dashboard restart mid-turn loses the message being answered; the dashboard stamps `interruptedAt` in `intercom.json` when it stops with the session's output under a minute old, and its next start, within 10 minutes, posts "resend anything from the last minute" through the hidden `finnamon notify --restarted` (v0.8.7.0). `channel off` stamps `state.inbound_off_at` and the daemon drops older messages (the plugin answered them). The one code gate on the plugin's `reply` tool is a `PreToolUse` hook, `finnamon hook reply-guard` (household chats only; attachments only charts); who may instruct the assistant is the plugin's allow list plus the skill's stranger rule. README has the setup steps.

**A reply arrives.** The daemon runs, with `cwd` = the repo:

```
claude -p --resume <session_id for this owner> --output-format json \
  "[Telegram, bill; replying to alert 1841] it is normal"
```

and sends `result` back to Telegram. **One shared session for the household**, resumed forever, every message prefixed with who is speaking (`[Telegram, jane] it is normal`); the agent remembers one thread the way a human assistant to both people would, and "what did Jane tell you about the Zelle thing?" works. Claude Code compacts it as needed; we manage nothing. The single `session_id` is kept in `state`; if a resume fails, the daemon starts a new session and continues. Sessions live under `~/.claude/projects/<repo-slug>/`, scoped to the repo folder but not inside it; an interactive terminal session in the same folder is a different session and does not bleed into the Telegram thread.

Because one session is shared, **the daemon runs `claude -p` calls strictly one at a time**: Telegram messages are queued and processed serially. Two simultaneous resumes of one session would corrupt it. This was already required (shared DB, shared cwd); now it is load-bearing. If two people message at the same moment, the second reply lands a few seconds later.

**Context comes from tools.** If the message was a Telegram reply, the prefix names the alert id. If not, the conversation itself usually says what "it is normal" refers to; failing that, the skill tells Claude to run `finnamon alerts --recent`. Claude looks things up; the daemon does no prompt engineering beyond the one-line prefix.

One Python package, `finnamon/`, plus a Claude Code skill and an MCP server over the same SQLite file.

Decisions baked into the schema:
- `transactions.amount` keeps Plaid's sign: positive = money out. Never negate on write; that was the old bug. `tests/test_sync.py` encodes the cases from `reference/old_plaid.py`.
- `transactions.name` is Plaid's raw string; `merchant_name` is Plaid's normalized one or NULL. The canonical merchant expression used everywhere is `COALESCE(t.merchant_entity_id, t.alias_canonical, t.merchant_name, t.name)`, where `alias_canonical` is one `merchant_alias` row per transaction as of `as_of`: an exact `name` match first, else the longest pattern (a `name` holding `%` matches with LIKE), ties by name (v0.5.4.0, issue 18). Aliases are written by `finnamon alias "<name>" <canonical>` (the assistant may call it; the pattern form needs three literal characters).
- Suppressions are structured, never expressions. A candidate is dropped when a `suppressions` row with `created_at <= as_of` matches on every non-NULL column (`kind`, `canonical`, `account_id`, `max_amount >= amount`). Written by `finnamon normal` only.
- **All three time-scoped joins (alias, category override, suppression), the canonical-merchant and effective-category expressions, and the mirror exclusion live in exactly one place: `detectors/_prelude.sql`**, a CTE named `tx` that `detect.py` prepends to every detector. A detector file is `SELECT ... FROM tx WHERE ...` and nothing else. `finnamon detect --sql <name>` prints the assembled query (eng review 4A). Since v0.7.4.0 there is a second copy, deliberately: the read paths that cannot prepend a CTE -- above all `finnamon query`, where the assistant writes the SQL and there is no call site to fix -- had no resolved relation to select from and fell back to the raw columns, so a merchant the household had renamed or recategorised came back under Plaid's old label (issue 23). `migrations/005_tx_now_view.sql` defines the same rule as the `tx_now` view, minus `suppressed` (it needs the detector's kind) and minus the `:as_of` scoping (a question about today's money wants today's aliases). Both files carry a KEEP IN STEP comment and `tests/test_detectors.py` fails on any column drift between them.
- Secrets (Plaid client id/secret, per-Item access tokens, Telegram bot token) live in `~/.finnamon/secrets.toml` at 0600, written atomically (temp + rename) and only by `init` and `link`. Everything Claude can change lives in SQLite. No secret is ever in the DB; no setting is ever in the secrets file (eng review 2A). Keychain is a TODO.
- `alerts.key` is the dedup key, so a detector can run four times a day and never message twice. `alerts.as_of` is the `settings.as_of` the detector ran with. `alerts.transaction_id` lets triage and notify group candidates that fired on the same transaction. `alerts.telegram_message_id` lets a reply be matched to the alert it answers.
- `recurring` stores Plaid's `last_amount` and `predicted_next_date` so `recurring_changed` is SQL, not date arithmetic on an enum. `first_date` is Plaid's first observed date; `first_seen_at` is when we stored it.
- `budgets.monthly_limit` is updated in place so `id` is stable and dedup keys hold within a month. `budgets.category` is either a primary or a detailed code; the detector matches `pfc_primary = category OR pfc_detailed = category`.
- `category_override` maps a canonical merchant to a `pfc_detailed`, joined time-scoped like `merchant_alias`; the effective category expression is `COALESCE(o.pfc_detailed, t.pfc_detailed)`. Written by `finnamon category <merchant> <category>`; Claude proposes, the CLI writes.
- `owner` on items and accounts records whose account it is; budgets have none. It is not used for routing: every message goes to the one household chat (`state.chat_id`). Joint detection and `mirror_of` are specified in User Workflow Step 5.

### Settings (what detectors can read)

`settings` is a real table (eng review 2A), read directly by `_prelude.sql`. `account_id = '*'` is global; a row with a real `account_id` overrides it. `detect.py` inserts the run's `as_of` as a row before running detectors and deletes it after. Detectors read a value with `COALESCE((SELECT value FROM settings WHERE account_id = t.account_id AND key = 'k'), (SELECT value FROM settings WHERE account_id = '*' AND key = 'k'))`. List-valued settings are one row per value. Keys:

- `as_of`: ISO timestamp, local time, written by `detect.py` at the start of the run. Every date expression in every detector uses `as_of`, never `now`. All date math is `'localtime'`.
- `dup_min_amount` (default 10), `dup_window_days` (3), `dup_ignore` (one row per canonical merchant)
- `low_balance_threshold` (per account; unset = detector skips the account)
- `budget_min_day` (5), `health_max_age_hours` (12)
- `outlier_multiplier` (3), `outlier_min_amount` (25), `large_amount` (200), `xfer_window_days` (5)

### Sync semantics

- `/transactions/sync`: for each page, apply `added`, `modified`, `removed` and save the cursor in one SQLite transaction. A crash mid-page replays the page; upserts converge. On `TRANSACTIONS_SYNC_MUTATION_DURING_PAGINATION`, restart from the cursor saved at the start of this run.
- `removed` deletes the row. A posted transaction carrying `pending_transaction_id` replaces the pending row with that id.
- Balances come from `/accounts/get` (no separately billed call). They are Plaid-cached and can be up to a day stale; fine for a weekly-keyed low-balance alert. "Numbers match the bank site" in Next Steps means transactions, not the live balance.
- Right after link, sync may return nothing or `PRODUCT_NOT_READY`. `PRODUCT_NOT_READY` is transient (never sets `items.status`); a first pull (no cursor yet) retries it for up to about two minutes, since 24 months at a large bank takes Plaid a while, and later pulls give up after 30 seconds and leave it to the next cycle. `items.first_synced_at` is set on the first sync that returns transactions. Detectors scope on it.
- Any Plaid error sets `items.status` and `items.last_error`. `ITEM_LOGIN_REQUIRED` means "run `finnamon link --update <item>`."

### Rule detectors (milestone 1)

All five are SELECTs over the settings table. Every alert row is inserted with `tier='rule'` and `as_of`. Item- and stream-derived rules put everything needed to explain the alert into `payload_json`.

- `sync_health.sql`: any Item with `status != 'good'` or `last_synced_at` older than `health_max_age_hours` relative to `as_of`. Key `health:<item_id>:<local date>`. This replaces Finnamon's silent Celery failures.
- `consent_expiring` (not a detector file: `sync.sync_accounts` raises it, since there are no webhooks for PENDING_EXPIRATION): `/accounts/get` returns `item.consent_expiration_time` for some institutions; within 7 days of it, one rule alert keyed `health:<item_id>:consent:<expiry>`, so it is sent once per expiry date. The fix is the same as a re-login: reply "fix <bank>". When two Plaid logins share the bank, both alerts carry `owner` and `duplicate` in the payload and say whose login and "fix <item_id>" instead (v0.8.12.0); `finnamon status` lists each item's `accounts` and `last_error` so the assistant can ask which one rather than pick.
- `duplicate_charge.sql`: same account, same canonical merchant, same raw `name`, same amount, dates within `dup_window_days`, both posted, amount at least `dup_min_amount`, neither leg in `TRANSFER_IN`/`TRANSFER_OUT`/`LOAN_PAYMENTS` (Venmo, Zelle, ATM, card autopays and mortgages repeat by design), neither suppressed, both `date >= date(items.first_synced_at)`. The raw-name match keeps two plans at one merchant entity from pairing (v0.8.0.1). Key `dup:<id_a>:<id_b>` with ids sorted.
- `new_recurring.sql`: `recurring.first_date >= date(items.first_synced_at)` and `first_seen_at` within 7 days of `as_of`, `status != 'EARLY_DETECTION'`. Key `recurring:<stream_id>`. Fires once per stream, ever.
- `low_balance.sql`: depository account with a `low_balance_threshold` whose latest `available` is below it. Key `lowbal:<account_id>:<strftime('%Y-%W', as_of, 'localtime')>`, at most one message per week while low.
- `budget_pace.sql`: per active budget, net month-to-date spend (`SUM(amount)`, refunds subtract) in that budget's category (via the effective category expression), posted, excluding `TRANSFER_*` categories, from day `budget_min_day` on. Projection = `spend * days_in_month / day_of_month` (days_in_month from `as_of`). Fires `budget:<id>:<yyyy-mm>:pace` when projection >= limit AND spend < limit; fires `budget:<id>:<yyyy-mm>:over` when spend >= limit. Mutually exclusive in any single run. No message under 100% projected.

Budgets: `finnamon budget suggest --json` (the numbers Claude reasons over in Step 3), `finnamon budget set <name> <amount> [--category X]`, `finnamon budget list`, `finnamon category <merchant> <category>`, `finnamon threshold <account> <amount>`. Milestone 4 adds `set groceries 650` by chat.

### Anomaly detection (milestone 2)

This is the differentiator, and it is built in two stages so it stays auditable.

**Stage 1, candidates (SQL, `detectors/candidates/`).** Each returns rows shaped like a rule but with `kind = 'anomaly:<name>'`, `tier = 'anomaly'`, and `transaction_id` set (or `stream_id` in the key for the recurring one). All scoped to `date >= date(items.first_synced_at)` and filtered through the suppressions join. Initial set:

- `first_merchant.sql`: canonical merchant never seen on any of this owner's accounts before `as_of`, amount >= `outlier_min_amount`. Key `anom:first:<transaction_id>`.
- `amount_outlier.sql`: amount > `outlier_multiplier` × median of this merchant's prior posted amounts (>= 3 priors; median via `ROW_NUMBER()`/`COUNT()` window functions, SQLite has no `MEDIAN`). Key `anom:outlier:<transaction_id>`.
- `new_category.sql`: `pfc_detailed` with zero prior transactions for this owner, amount >= `outlier_min_amount`. Key `anom:cat:<transaction_id>`.
- `no_source.sql`: `merchant_entity_id IS NULL AND merchant_name IS NULL` and no alias for `name`, amount >= `outlier_min_amount`. The "I can't tell what this is" case. Key `anom:nosrc:<transaction_id>`.
- `unmatched_transfer.sql`: `pfc_primary IN ('TRANSFER_IN','TRANSFER_OUT')`, `abs(amount) >= large_amount`, with no transaction of `abs(amount)` equal and opposite sign within `xfer_window_days` on any account we hold. `INCOME_*` is excluded (paychecks are not transfers). Payments to cards or accounts we don't hold will still surface here; that is what suppressions are for, and triage sees the counterparty name. Key `anom:xfer:<transaction_id>`.
- `recurring_changed.sql`: `abs(last_amount - avg_amount) > 0.2 * avg_amount`, or `predicted_next_date < date(as_of, '-7 days')` with `last_date < predicted_next_date` and `predicted_next_date >= date(first_synced_at)` (a date missed before the first sync is backfill, not news). Streams Plaid marks inactive (`is_active = 0`) never count. Key `anom:rec:<stream_id>:<yyyy-mm>`.

A single transaction can trip several candidates; that is expected and handled in triage, not by narrowing the SQL.

**Stage 2, triage (a Claude Code skill, `/triage`).** Bill: use Claude Code as the harness here too. After detect, if any anomaly alerts have `verdict IS NULL`, the daemon runs `claude -p "/triage" --output-format json` in the repo (a fresh session each time, not the household conversation session; triage is a batch job and its tool calls would pollute the thread). The skill:

1. `finnamon alerts --untriaged --json` to get candidates grouped by transaction.
2. For each group, whatever lookups it needs: `finnamon query "..."` (read-only SQL) for the merchant's history, the account's typical amounts, recent similar transactions; `finnamon budget list`; `finnamon normal --list` to see what Bill already called normal.
3. Decide, as this person's finance assistant reading their statement, whether to mention each transaction, with confidence high (looks like fraud, an error, or money leaving with no clear source) or low (unusual but plausible), and one sentence why.
4. `finnamon triage set <transaction_id> promote|suppress high|low -` per group, the reason on stdin through a quoted heredoc. It refuses a reason given as an argument: a double-quoted one has lost its `$` signs before the command sees it (#63). Run by a person (never a Claude session: triage or chat) on a group with nothing left untriaged, the same verdict replaces only the reason of its stamped candidates (a repair); verdict, confidence and sent state stay. That command is the only write; it stamps every candidate in the group, and a single candidate's key stamps its whole transaction, so two detectors on one transaction can never split promote/suppress. A detector that fires after its transaction was judged or resolved takes that verdict and resolution (`detect.join_family`).

`triage.py` shrinks to: run the skill, then verify every untriaged group now has a verdict. Any group still `NULL` after the run increments `triage_attempts`; on the third consecutive failure the group is marked `suppress` with reason `triage_unavailable` AND a rule alert `health:triage:<local date>` is inserted so Bill is messaged that triage is down, the same way he'd be messaged about a dead sync.

Cost is a handful of tool calls per candidate group instead of one shot; a few candidates a week after the first month. The trade is more tokens for less code and a prompt that lives in `SKILL.md` where Bill can edit it in plain English.

The LLM can only promote or suppress rows that SQL produced. Every suppression is kept with its reason; `finnamon triage --suppressed` lists what it chose not to tell you.

**Delivery (premise 9).** `notify.py` sends alerts where `sent_at IS NULL AND (tier='rule' OR (verdict='promote' AND confidence='high'))`, grouped by transaction so one transaction is one line. `confidence='low'` accumulates. The roundup fires on the first run where `as_of` is a Sunday, or the Monday after a Sunday with no run (Monday counts as the Sunday before's week), and `state.last_roundup_week` is not that week: one numbered "things I noticed this week" message, each item with its reason, or, when nothing is waiting, one all-quiet line (accounts watched, the stalest bank's last sync, the week's transaction count, alerts already sent or still waiting), so a quiet week never looks like a dead watchdog. Then `last_roundup_week` is updated; a forced `finnamon notify --roundup` on another weekday sends but does not stamp the week. Nothing with `verdict='suppress'` is ever sent.

**Feedback.** `finnamon normal <canonical> [--kind K] [--account A] [--max-amount N] [--note ...]` writes a structured `suppressions` row. In milestone 4, replying `normal` to a high-confidence message suppresses that alert's canonical merchant (on a `duplicate_charge` alert, only on that account and up to that amount, so a bigger double charge there still fires); replying `normal 3` to a roundup suppresses item 3. Over time the candidate set shrinks to genuinely new things, which is the point.

**Token cost.** Zero on runs with no untriaged candidates. In practice a few candidates per week after the first month.

### Delivery mechanics (milestone 1)

- `telegram.py` is three functions over `https://api.telegram.org/bot<token>/`: `sendMessage` (text, `parse_mode=HTML` with escaping applied to every merchant string), `sendPhoto` (multipart, for charts), `getUpdates` (long-poll, `offset`, `timeout=25`). urllib, no SDK. Everything is sent to the household chat in `state.chat_id`; `owners.telegram_user_id` is used to accept messages only from household members and to label who is speaking.
- One Telegram message per transaction (`store.ALERT_GROUP`: the alert's `transaction_id`, else account + date + amount + name for an anomaly, else its key), so every alert sharing a `telegram_message_id` is one transaction and a quoted reply resolves exactly (eng review 5A). The clearest of its alerts is the line; all are stamped together, and one that fires after the transaction was told joins that message unsent. `finnamon alerts` (and so the dashboard) shows one alert per transaction with the rest under `folded`; Dismiss, `normal --alert` and Undo cover them all. A burst (a bad first sync) is throttled with a sleep to stay under Telegram's per-chat rate. The 4096-char limit is enforced by splitting. `sent_at` and `telegram_message_id` are set per alert only on a 200; a 429 backs off and leaves the alert unsent for the next run.
- `run.py` catches any unhandled exception, logs it, and inserts a rule alert keyed `health:run:<error class>:<local date>` so a persistent failure is one message a day, not four (eng review 6A). Only if that insert itself fails does it attempt a direct send. If Telegram is unreachable, the log is the record and the heartbeat retries hourly; a Telegram outage is the one silence this design accepts.

### Scheduling (milestone 1)

- `finnamon init` detects the OS and installs three units (two when the dashboard was skipped: no `web/node_modules`). macOS: LaunchAgents in `~/Library/LaunchAgents` (user session, never LaunchDaemons): `com.finnamon.daemon` with `KeepAlive true` running `finnamon daemon`, `com.finnamon.heartbeat` with `StartInterval 3600`, and `com.finnamon.web` (`KeepAlive true`, `node web/server.js`); `WorkingDirectory` = repo, absolute venv `python3`, `HOME`/`PATH` set (PATH must include `claude`); `StandardOutPath`/`StandardErrorPath` to `~/Library/Logs/finnamon/`. Linux: `finnamon-daemon.service` (`Restart=always`), `finnamon-heartbeat.timer` (`OnUnitActiveSec=1h`) and `finnamon-web.service` (`Restart=always`) as user units with `loginctl enable-linger`; logs via `journalctl --user`. `finnamon install` repeats that step on its own, over a running daemon: on macOS it boots the old service out and waits for launchd to drop the label before bootstrapping (bootstrapping into that gap fails with EIO, so `install` waits and retries on EIO only); on Linux it `systemctl --user restart`s the daemon after `enable --now`, which alone leaves the old code running.
- **Picking up a release (v0.7.0.0): `finnamon update`, not `install`.** Reprovisioning is the wrong tool for new code: rewriting the units reloads every job, and reloading the dashboard job starts the household's assistant fresh. `update` leaves the units alone. It compares them first (`scheduler.drifted_units`, before anything is pulled or migrated) and sends you to `install` when a release moved them, because restarting into a definition launchd no longer has would keep running the old one silently. Then it pulls `--ff-only` (refusing a tree with uncommitted changes to *tracked* files: an approved detector under `finnamon/detectors/` is untracked by design), takes the run lock so it never migrates or restarts on top of a sync in flight, migrates, and restarts only what went stale — `scheduler.services_for` maps changed paths to jobs against a denylist (`INERT`: `web/public/`, `docs/`, `tests/`, the top-level markdown), so a page-only change restarts nothing and anything it cannot place restarts both. A denylist rather than a whitelist because the paths that would slip through a whitelist are the assistant bundle's (`finnamon/assistant_bundle/`: its settings.json and skills), the assistant's permission set and instructions, read once at startup. `restart` then checks each job is actually still running (launchd `kickstart` returns when a job respawns, not when it stays up) and names the ones already moved if a later one fails. The session survives because the dashboard resumes it by id, and because the daemon kills its own `claude` children on SIGTERM: two processes on one session id is the one thing that corrupts a conversation.
- The daemon runs sync every 6h on its own clock (`state.last_run`), so a sleeping laptop simply resumes; no calendar catch-up logic needed.
- Heartbeat: if `state.last_run` is older than 8h and `state.last_heartbeat_text` is not today, send one message and record it. It is a separate process so it can notice a dead daemon. A laptop that slept overnight wakes with a stale `last_run` and a daemon about to catch up, and launchd fires the heartbeat on wake too, so: it first gives the daemon up to 2 minutes to stamp `daemon_alive_at`; a daemon still silent is dead, and that is reported at once. A live daemon gets a grace (`heartbeat_deferred_at`, cleared by the next successful run), and the sync is reported only if it is still stale 50+ minutes in: syncs that keep failing, or one hung behind a live Telegram thread. A wake restarts the grace unless a sync attempt finished and failed since it began, so a laptop that slept mid catch-up is not an outage. A deferred check never uses the day's slot. Separately, `daemon_starts` holds the daemon's recent start times: a clean stop takes its own entry back and 10 minutes of uptime clears the list, so 3 or more mean the supervisor keeps restarting a daemon that keeps dying, reported once per loop (`crash_loop_reported`) with `daemon_last_error` and where the log is (never "run `finnamon daemon`": a second daemon on one session corrupts it).
- `run.py` takes an `flock` on `~/.finnamon/run.lock` (`run.lock()`) so a manual `finnamon run` can't overlap the daemon's sync thread; `finnamon sync`, `finnamon link --remove` and `finnamon account remove` take the same lock, and refuse (`Locked`, retry in a minute) rather than wait; the pending-link check (`link --finish`, the daemon's tick) takes it too and reports "waiting" when it is held, and the re-login check (`link.check_updates`) takes it to sync a bank and retries on the next tick when it is held. WAL + `busy_timeout` cover Claude's CLI calls and the MCP server reading concurrently.
- Telegram privacy mode must be **off** for the household group (BotFather → /setprivacy → Disable, then re-add the bot to the group). `finnamon owner add` and the daemon at startup verify `getMe.can_read_all_group_messages`; if false, the daemon says so in the chat and stays in DM mode. The bot is also made a group admin (eng review 3A). Because the bot then sees every group message, the finnamon skill instructs Claude to answer exactly `NO_REPLY` to anything not addressed to it, and the daemon sends nothing in that case; the group is finance-only by convention (tension 1).
- No OS permission grants are needed on either platform; that was the iMessage design's cost and it is gone.

### Plaid Link

`finnamon link [--update <item_id>]` calls `/link/token/create` with `hosted_link: {}`, `products: [transactions]`, `optional_products: [investments]` (holdings where the institution supports it) and `transactions.days_requested: 730` (fixed at Item creation; Plaid's default of 90 is too short for `budget suggest`); update mode (`--update`, a re-login) passes `access_token` and changes nothing else: product consent is fixed at Item creation, so to add holdings to an Item linked before investments were requested, `--remove` it and link again. It prints the URL (and with `--telegram` also sends it to the household chat, which is shared, so never by default), polls `/link/token/get` until `link_sessions[].results.item_add_results[].public_token` appears, exchanges it, and writes the token to `secrets.toml`. `finnamon link --remove <item_id>` is the inverse: `/item/remove`, rows dropped, token forgotten, under the run lock. The non-blocking shape the assistant uses: `finnamon link --start` creates the session, stores `{owner, link_token, url, started_at}` in `state.pending_link` and returns (a still-open session is reused, never orphaned); the daemon's sync tick, or `finnamon link --finish`, polls under the run lock (`link.check_pending`: waiting, closed, expired or linked), exchanges, syncs, announces, and reports mirror candidates without merging them. A session the person closed without adding a bank stays pending because the same URL can be reopened (the chat is told once); `INVALID_LINK_TOKEN` or a malformed row drops the session so a fresh `--start` can open one. The row records the `item_id` right after the exchange, so a crash between exchange and sync is resumed from that Item and the single-use public token is never exchanged twice; the row is cleared only once the link completes, and expires 10h after start (4h session + 6h token window). From a Claude session only `--start`, `--finish` and `--update <item_id> --telegram` are accepted (the last is `link.start_update`: non-blocking, the update-mode link always goes to the chat; the blocking form stays a person's), `--owner` must name an existing household member, and a `/triage` run cannot link at all. The links a Claude session sends to the chat are rate-limited (v0.8.12.0, so a prompt-injected memo cannot fill the chat with link tokens): `--update` at most once per Item per 15 minutes (a link lives 30), and `--update` plus `--start --telegram` at most 6 per household per 24h, kept in `state.update_links` and counted only once the link reached the chat; a refusal is an error the assistant relays as is. A person at a terminal is not limited. The dashboard's Reconnect button runs `link --web --update <item_id>` (refused from a Claude session): the URL comes back to the page instead of the chat, with no rate limit, and a session under 20 minutes old is handed back rather than opening another. Every update-mode session, from the chat or the page, is kept in `state.update_sessions`, and the daemon's 60s tick (`link.check_updates`) polls each one; once it is over, that bank syncs at once under the run lock, its open `health:<item_id>:` alerts are resolved `reconnected` (the consent alert only when Plaid returned a public token, proof the login happened) and the chat hears "<bank> is reconnected." A Plaid outage during that sync keeps the session for the next tick; a session closed without logging in is dropped quietly. Hosted Link provides the https OAuth redirect that Chase-style institutions need for terminal and Telegram links; the web dashboard's in-page Link uses `link --token [<https redirect>]`: the page passes its own address only when it is served over HTTPS (`x-forwarded-proto`, e.g. tailscale serve), and that address must be registered in Plaid; on plain http no redirect is sent (Plaid accepts HTTPS only outside Sandbox) and OAuth banks open in a popup.

## Build log (2026-09-19)

Built in one session after the eng review; all milestones' code paths exist and are tested (71 offline + Sandbox E2E tests, 2 evals against real Claude). Deviations from the text above, each deliberate:

- **Plaid over urllib, not `plaid-python`.** Six endpoints; the generated client's request models weren't worth a dependency. `finnamon/plaid_api.py` is 90 lines and was validated against the Sandbox. Core package has zero runtime dependencies; `matplotlib` and `mcp` are extras.
- **`reference/old_plaid.py` never existed.** The backend submodule couldn't be cloned (private). The Sandbox probes and `tests/e2e/test_sandbox.py` are the sign-convention oracle instead.
- **`as_of` is a bound parameter (`:as_of`), not a settings row.** Same reproducibility guarantee, no temp-table state. `detect.py` also substitutes `__KIND__` in the prelude so the suppression match is per-detector without repeating the join.
- **`category_override` carries `pfc_primary` too**, resolved from the taxonomy at write time, so a budget on a primary category counts overridden merchants correctly.
- **`amount_outlier` uses a median over history before the 7-day window**, not per-row (`ponytail:` comment in the file); per-row windows are quadratic for no gain at household scale.
- **`budget_pace` materializes the `tx` CTE once per run** (SQLite's choice); only the `duplicate_charge` self-join is index-checked in tests. Fine at household scale.
- **The daemon has three threads, not two:** sync, Telegram poll, and a serial conversation worker fed by a queue, so a slow `claude -p` never blocks `getUpdates` either.
- **Sandbox quirk recorded:** a second `/transactions/sync` on a fresh Sandbox Item re-sends rows as `modified`; upserts converge, tests assert the row count, not a zero page.
- Milestone 6 (`investments.py`: holdings sync, net worth) and 7 (`owners.py`, joint detection, mirrors, failover) are built and unit-tested but not exercised against real accounts yet.
